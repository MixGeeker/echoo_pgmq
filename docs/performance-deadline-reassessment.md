# 轮询截止时间复核：维持不重开

综合此前四臂30单元实验与新trace复算，结论仍是**不重新实施或测试deadline夹紧，也不把空claim的截止时间重锚到完成时刻**。新数据解释等待机制，但不足以推翻旧的不一致延迟和额外查询代价；优先处理业务事务占用全局容量锁的实际影响。本次没有改产品代码或启动新负载。

## 新trace实际说明什么

只使用原七计划B的三个native窗口，其原G0至G3门禁均通过；不是后来bridge-phase漂移失败的P2。范围为Linux PG18.6、1P1C、1KiB、200消息/s加200TPS、poll2ms、89.99045秒，产品事件循环源码与450一致。

本轮now_ms使用PostgreSQL instr_time，冻结Linux头文件选择CLOCK_MONOTONIC，与服务端trace同钟；sender_visit记录实际整数毫秒next_poll，故可以直接比较这两个服务端记录，不需要减客户端时钟。原始now_ms采样瞬间和数据库精确返回瞬间并未记录，只能用相邻标记区间约束；标记也有测量/调度开销。该同钟结论不能直接外推Windows。

- 34,709次空claim中，loop标记到empty返回标记平均0.10020ms、中位0.08588ms、p99为0.31980ms、最大2.92956ms；实际loop采样到完成的平均上界0.10313ms、p99上界0.32864ms。中心值很小，罕见大值可能含失调度。把下一次轮询改为从完成时算起主要会延后轮询，没有收益证据，停止该方向。
- 80,383个完整loop中，27,661次等待满足：consumer有credit、inflight为0、保留未来deadline、本loop未claim、前次IO提前唤醒、随后又申请完整2ms；其中25,595次跨过记录的deadline。
- 再收窄到成功publish计数尚超过成功claim计数、并且只因超时返回的1,500次等待，deadline之后的实际等待区间合计2.49789秒，中位1.83700ms，p99为2.08469ms。这是固定单队列工作负载的发布/领取余额，不是直接SQL深度采样。
- 在这些记录上回放整数毫秒剩余timeout，1,325次名义上可少申请1ms、53次少2ms、122次仍为2ms，合计1.431秒；三个cell分别276/572/583ms。它是请求timeout的包络，不是已实现延迟下降、CPU节省或产品加速。

完整buffer资格、link关闭状态和transport状态没有记录，因此不能证明每个选中等待都可立即执行。提前轮询会改变后续时间排列，也可能读到空队列并增加数据库工作；不能简单把2.498秒从实测总时延中减掉。这个约90秒中的小包络不足以压过旧负结果。

## 曾考虑的窄条件仅保留记录

可辨别的设计条件是：pump前next_poll大于0、pump后未变，且现有credit/inflight/关闭状态/buffer条件均满足时，才按最近保留deadline限制timeout。next_poll=0的即时路径及fresh-empty自身首次完整等待保持；不改时钟，不因ACK重设deadline。该描述用于日后与旧源码比对，**不是当前实施或实验建议**。

风险包括额外空查询、公平性变化，以及对credit或buffer阻塞的链接错误地请求连续零超时。没有新证据前，不继续扩时钟、trace或新调度基础设施。本轮只有只读分析；API、事务、权限、资源限制、持久确认和至少一次语义没有变化。

复算来源为旧七计划native trace、其独立窗口/门禁结果、冻结instr_time.h及原四臂汇总；源和trace散列、单调事件、正常footer与连接生命周期均校验。原环境分析材料位于poll-deadline-assessment；旧raw仍属此前证据包，未为本文重跑。本轮存储为volatile overlay/tmpfs、只有CPU亲和性，不能作为SSD、Win11、真实ERP或生产性能资格。安全/parser/fuzz/资源耗尽/新故障范围继续暂停。

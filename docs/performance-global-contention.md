六个争用样本都先通过pg_blocking_pids证明worker确实等待本轮外层SQL后台PID，wait_event为Lock/transactionid，然后保持约150ms并正常COMMIT。两类远端确认均约157–158ms，表明全局容量锁会将一个业务事务的等待传到另一队列。释放之后均正常确认、对账并排空；没有触发1秒锁超时，没有拒绝、故障注入或容量耗尽。

这确认了已知的容量记账取舍，不是新优化收益：SQL入队与业务同事务保持原子性，硬全局容量计数的行锁持续到外层事务结束。不同队列因此也可能互相等待，Accepted消费结算同样受影响。测试没有改变这个锁序或提交语义。应用应让入队所在业务事务保持必要且短，避免在持锁事务中等待外部网络或用户操作；不能为省等待而拆开需要原子提交的业务与消息。


## 不放宽严格容量与同事务原子性的改善顺序

以下是根据已确认锁持有范围给出的使用建议，尚未在真实ERP联测，不是本轮测得的性能收益：

1. **业务逻辑允许时，把enqueue放到事务最后、紧接COMMIT。** 业务表写入与消息仍在同一事务，容量不足时仍让整个事务失败并回滚。这样全局限额锁不必覆盖入队之后原本可以先完成的业务步骤。不要把消息改成业务提交后的另一次无保护发送。
2. **所有相关路径保持一致的锁顺序。** 建议先完成业务行的必要锁与修改，再进入队列容量/消息路径。若某条路径先入队再等业务行、另一条先锁业务行再入队，可能形成循环等待；需要同时检查调用点和业务触发器，不能孤立移动一行就保证无死锁。如果后续业务必须使用返回的message ID，剩余事务应保持短。
3. **减少持锁区间的应用往返和非数据库等待。** 外部网络/用户交互以及不依赖本事务最终业务状态的准备工作先完成；需要多条消息时，可在既有API和同一事务中组织为少量数据库往返，但不要无界增大事务批次。消息内容仍须对应本事务正确的业务结果。不要通过调大锁超时掩盖持续争用。
4. **先量实际长事务与等待，再决定是否需要架构改动。** 本次150ms模拟的是事务持有锁的时间，不是150ms真实ERP CPU或磁盘工作；就算把enqueue移到末尾，业务仍可能通过业务行锁、CPU或I/O影响其他请求。

示意顺序：BEGIN → 完成必要业务数据库写入并得到事件所需数据 → 调用现有enqueue/ enqueue_binary → COMMIT。公开API、严格总消息/字节限额和提交确认顺序都不需要因此更改。

当前内部实现仍需对共享容量行进行事务协调。已有0.1.2预留候选减少部分重复锁/行更新，但原生端到端结果没有稳定净收益，不能用来宣称消除了外层业务事务的锁寿命。增加worker也不能消除对同一全局限额行的等待。按队列预分配严格额度等方案在理论上可保持总上限，却会改变空闲额度借用、容量利用和迁移/恢复约束；属于单独架构选项，不能静默改成近似计数、异步额度释放或预先确认。本轮不实施这些方案。

## 验证与证据边界

- 2类场景各2个无争用基线、3个争用样本，共10次；每轮新建不同A/B队列，测量链接在业务事务之前建立。消费结算先正常发布和领取，采用receiver-settle-mode SECOND，随后才发送本地Accepted并等远端结算。额外种子/排空操作明确未计入10个测量端点。
- 375条原始事件已离线复核：6次真实跨队列锁等待、31份队列/全局计数与持久行汇总一致、全部10轮排空及最终空队列、20个客户端AMQP关闭/TLS关闭/stdin EOF/回收顺序和exit0。前后实际模块映射的路径、inode、device、进程身份及SHA保持一致。
- 正文/metadata、保存的wire字节、generation/attempts/owner以及提交前不可见性由冻结脚本中的运行断言验证。原始stored行和完整receipt没有单独输出到事件，离线复算不声称重新读取这些未保留的数据。PG18.6及fsync/full_page_writes/synchronous_commit=on由运行脚本断言，实际SQL设置行也未单独输出。
- Node与Python时钟没有交叉相减。Python“COMMIT发送→stdout确认事件到达”包含IPC和调度延迟，既不是数据库内部提交时间，也不是纯网络延迟；基线还包含提交后向客户端发go命令的开销。保留COMMIT返回与确认事件可能的先后次序。
- 只观察少量正常操作，不计算p95，不推算容量、真实ERP劣化、Windows/Win11、SSD或长期可靠性。本轮为云端volatile overlay，PG同步设置开启不能证明物理持久介质耐久。未改变暂定ERP/DB p95≤10%的历史评分。
- 这补的是Linux固定预览的独立正常场景证据。原有长事务超时拒绝测试仍未恢复，当前ordinary矩阵清单也未因本次改变。完整安全/parser/fuzz/新故障资格继续暂停，blocked_security_review未解除；没有合并或升级已发预览。

# 原生发布后唤醒试验：普通固定负载结果（2026-09-30）

## 当前决策与可比性限制

**已于37fc015撤回唤醒实验，恢复此前原生代码。撤回的理由是尚未建立稳定收益，并非已证明唤醒代码导致退化。** 历史472e626试验与全部不利数据保留。

**本轮PG-only基础负载本身未能稳定达到设定200事务/秒，且与旧轮次来自不同共享runner，不能作为严格A/B。** 下文是完整的诊断性观察；数据收集/对账有效不等于性能比较条件充分。下一步先做同机交错、随机顺序的短机制实验设计，并要求PG-only稳定性门禁；不立即重复第三轮长测。

## 观察结果

本轮完成 **27/27 单元**，每单元 **30秒预热 + 120秒测量**，完整原始证据已逐文件验真并由两份离线脚本独立复算。**本轮结果不支持将该唤醒候选认定为整体性能改善或验收通过。**

- echoo **11/12** 消息单元的实际发送到达率低于目标95%；实际到达率范围 **67.900%–97.219%**。RabbitMQ为 **99.704%–100%**，无低于95%的单元。95%在此用于披露未达到设定负载，并非新设或替换验收阈值
- echoo的1×1端到端p95跨运行中位数有所下降，但p99在全部四组均上升；4×4/200的三轮p99为 **143.970、128.843、99.016ms**。不能只展示改善的p95或删去长尾与慢轮次
- **DB p95相对同轮PG-only基线增幅≤10%：两侧均0/12通过，共24/24未达标**，阈值未修改。绝对毫秒与同轮百分比均保留
- 全部阶段 **1,000,146** 条尝试、Accepted和唯一接收数一致，观察到 **0 丢失、0 重复、0 未确认发布、0 校验/run-ID错误**；各单元最终排空。普通流量对账成功不等于性能目标或故障可靠性通过
- **独立PG基线自身也明显异常于旧轮次**：三轮仅165.242–172.717事务/秒（目标200），DB p99为19.743–37.002ms；旧轮次基线约199.9事务/秒、p99为1.513–1.695ms。RabbitMQ混跑的合成DB同样存在长尾。这是重要混杂因素，不能把本轮差异直接归因于wake
- 新旧试验在不同GitHub VM执行，runner image也变化；下面的跨运行差异**不能单独证明由唤醒代码导致**。PG基线和RabbitMQ对照本身亦变化，实际完成负载还明显不同

## 试验条件与变化范围

此次代码候选仅在原生发布持久化成功后唤醒符合条件、队列匹配的消费者；SQL、确认/持久化语义、轮询2ms和候选门槛保持原定义。结果本身不证明该唤醒设计的具体根因。

- 整个服务端栈共用 **2逻辑CPU（0–1）、4GiB RAM、0 swap**：echoo为PG+worker；RabbitMQ为PG+RabbitMQ/Erlang。前后Docker配置和cgroup均读回验证，PID上限512
- 客户端、合成DB客户端及采样器使用另2个CPU（2–3），在服务端预算外。runner共4逻辑CPU、约15.61GiB，不能称总机4GiB试验
- 原始build-packages.txt在两轮全部54单元字节一致；python-inputs.txt、按代理匹配的postgresql.conf、rabbitmq.conf亦字节一致。与旧试验提交对比，bench Python/Dockerfile、SQL和CMake未变，相关运行源码仅src/echoo_pgmq.c变化；普通CI/文档/测试文件另有变化
- 每单元独立新Docker卷，27卷互异；工作树干净，同一不可变镜像 `sha256:8b4f9daeefffeeb96fd9c092afcb6cdc1c4a9055dca2fe69d6308a029ecfdc1b`
- PostgreSQL18.6、RabbitMQ4.0.5、Proton0.40.0、Python3.12.14；Linux6.17.0-1022-azure，runner image **20260927.320.1**（上一轮 **20260920.314.1**）
- 标准RelWithDebInfo，test hooks关闭；AMQP1.0、mTLS+服务端名称校验、SASL EXTERNAL、1024字节正文、durable消息、逐条等待远端Accepted、消费者手动Accepted、credit32，每发布连接最多1条未确认

PG-only基线的三轮实际事务率/p99分别为 **172.717/s与19.743ms、165.242/s与37.002ms、170.183/s与24.512ms**；旧轮次对应约199.9/s和1.513–1.695ms。新基线较低的p95并不代表整个分布更好。RabbitMQ混跑DB也降至159.675–186.500/s，单元DB p99为2.741–43.522ms，但RabbitMQ消息完成率仍接近200/400/s。echoo与这些合成DB都使用PG持久化路径，值得控制和区分环境因素；这里不把这种共同变化作为根因证明。

额外[原始时间关联统计](../bench/results/wake-pg18-20260930/timing-associations.json)仅对已完成数据离线分析，以≥20ms作描述性分组（不是新的验收阈值）。例如r3-echoo-1×1/200共有469条E2E≥20ms，其中467条同ID发布确认也≥20ms；其独立合成DB p99为85.992ms。许多消息长尾时段与独立DB慢事务重叠，说明只看接收端p95不足以描述现象。

**不能据此定位到PG COMMIT、WAL flush、worker唤醒或服务端调度。** 发布确认延迟包含服务端和客户端全路径；合成DB在独立连接上，不是echoo内部事务。原始数据没有服务端阶段跨度、锁等待、逐消息WAL刷盘时刻或运行队列轨迹，约0.5秒一次的资源采样也不足以归因短时停顿。全程未见配额节流，只排除采样区间的cgroup CPU配额节流这一已记录现象。

## 结论边界与后续决策

1. 这轮候选不能以“唤醒优化已提升性能”通过；应保留当前负面结果，并在新的动作获授权后先查明正常负载下的长尾、等待与实际发送不足。此报告不修改代码、不触发新试验
2. 若另行授权验证因果，需要更强的环境控制、交错旧/新版本和重复基线；继续保持fsync、持久化/确认语义、原10%门槛，不以减小工作量换取通过
3. 每单元仅150秒活跃负载，短于300秒checkpoint_timeout；不覆盖长期checkpoint/vacuum、离线追赶、容量上限、24小时、复制、崩溃或断电语义
4. 主验收仍需真实Win11 x64、4核/8GB/SSD、原生PG18与实际ERP证据。Linux云runner的合成普通负载不能替代这些证据

本页和紧凑摘要只记载已经完成的授权普通试验。所有历史失败、慢单元、方差和门槛未通过记录均保留；暂停中的资格验证未恢复。

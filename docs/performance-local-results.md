# 云端同机机制优化与无原生插桩确认（2026-09-30）

## 结论与采用决定

七项 SPI 计划复用在无原生插桩的三对实验里，采样自有服务进程 CPU 分别下降 **9.29%、6.59%、12.77%**；但第 2 对确认 p99 **+16.81%**、投递 p99 **+6.76%**、合成 DB p99 **+31.17%**，前两对最大延迟也变差。它是有一致 CPU 方向信号、但尾延迟尚不稳定的候选，当前产品采用决定仍保留 A。没有用更好的 p99 隐去坏极值，也没有因此降低暂定目标。

[优化草稿 PR2](https://github.com/MixGeeker/echoo_pgmq/pull/2) 保留候选及回归；产品工作分支的基线没有换成候选。完整优化/审核条件未满足，未合并 main、未正式发布。这里是单 producer/consumer 固定负载的普通机制实验，不是容量上限、RabbitMQ 复赛、Win11/SSD 或真实 ERP 资格。真实 ERP 仍按约定留待共同联调。

## 环境、负载和预先固定的门禁

- Debian 13.6、Linux 6.18.44、GCC 14.2、PostgreSQL 18.6、Proton C/Python 0.40、OpenSSL 3.5.7；官方源码校验和、构建参数与实际加载库身份都保留
- 可见 9 个逻辑 CPU、约 9.7GiB 主机内存；server affinity 为 0/1，client/controller/observer 为 2/3。**只有亲和性，没有强制 cgroup CPU quota、4GiB 内存上限或 swap 限制**；不是此前 GitHub 容器总资源预算
- **workspace overlay 为 fsync=volatile，/tmp 为 tmpfs**。PG fsync/full_page_writes/synchronous_commit 开启，队列表 logged；仍不能证明持久介质性能或掉电可靠性
- 每轮相同 BA、BA、AB，seed 20260930；G0→P1→G1→P2→G2→P3→G3。四个 PG-only gate 各 5 秒暖机+20 秒测量，六个 cell 各 5+30 秒；单次 600 秒硬边界，失败即结束、不重试刷绿，全部正常停止
- gate 全窗及前后 10 秒开始/完成均 ≥190 TPS、0 错误；相邻 gate 吞吐漂移 ≤5%，p99 差值 ≤max(1ms, 前一 gate p99×50%)。各轮全部四 gate 和三相邻漂移均通过，不因结果调整门槛
- 每 cell 为 1 producer、1 consumer、1KiB payload、目标 200msg/s，同时合成 DB 目标 200TPS；credit32、poll2ms（产品默认50ms）、mTLS/EXTERNAL、durable、逐条等 Accepted、手动消费确认。一条在途及无追赶突发的节拍会在变慢时少发，不能据此推算开放到达容量
- 合成 DB 是 1,000 行库存表：事务中单行 quantity+1，再对 100 行范围 sum，随后提交。其毫秒延迟不是实际 ERP 性能；暂定 ERP p95≤10% 目标仍未验收
- 前三轮含各 arm 248MiB 预触碰 native trace 缓冲和观测开销；第四轮去掉它，但 client 计时/ID/checksum、psutil 与 PG I/O timing 仍开。不同轮绝对分数不可作严格 A/B，不能据此推断新增三条 SET 的独立增量收益

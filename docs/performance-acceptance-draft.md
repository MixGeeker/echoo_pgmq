# echoo_pgmq 分层性能验收草案

2026-09-30 · **待审阅，不是已批准的验收标准**

核对版本：PR #2，`0e619694b683ae05697fe8c804385456e342a6a5`。本稿整理已有约定并提出待决参数，不改变现有阈值、历史评分或运行时，不阻断已授权的普通优化。本稿口径核对仅阅读文档与代码，没有为编写本稿重新运行负载、CI或资格测试。

## 1. 已有约定与尚未定案的部分

- 主目标为 **Windows 11 x64、4核、8GB、SSD、原生 PostgreSQL 18**；ERP 与队列部署在同一数据库。Linux 与原生 Windows 都需普通兼容证据，PG16/17为补充。
- 容量方向为实际门店观测峰值的 **2倍**下积压不持续增长。真实峰值及其统计窗口尚未知，不能给出产品 msg/s 容量承诺。
- **200/400 msg/s、1KiB**是现有固定负载试验点，不是最大吞吐、业务峰值或已通过容量。此前约 **4–6ms** 是特定条件下的观测，不是延迟门槛。
- ERP/合成DB **p95增幅≤10%仍为暂定目标**。既有合成试验未达标；真实ERP尚未联调。合成库存事务不是ERP，也不代表ERP全请求响应时间。
- 生产者只能在数据库提交成功后收到 durable Accepted；提供至少一次语义，允许合法重投；已Accepted消息不得无故丢失。正常重投、确认丢失后重试与业务重复副作用必须分别计数，不能把“任何重复为零”写成产品语义。
- 消息绝对延迟SLO、CPU/内存限制、长稳时长和回归阈值尚未冻结；“全面优于RabbitMQ”不是硬目标。普通性能改善不能抵消语义问题，也不能自动完成生产资格。

## 2. 三层证据分别回答什么

### 第一层：易失云环境的普通机制证据

用于回答固定改动是否减少某条路径的成本，以及是否出现可重复的尾延迟或CPU代价。必须固定源码提交、实际加载库散列、SQL/配置、依赖、客户端、计时方法和观测开销；同一主机相邻交错配对，保存预定顺序及所有有利/不利结果。

延用对应实验已经固定的PG-only稳定门禁、前后漂移和实际负载检查；前置门禁失败就不开始比较，后置失败使受影响配对无效并按原规则停止。无效数据保留但不进入有效效应估计，禁止事后放宽门槛追认。门禁通过也仅是可比性筛查。

现有workspace为`overlay fsync=volatile`/tmpfs，CPU亲和性不是硬配额。保持logged表、fsync/full_page_writes/synchronous_commit以及提交/Accepted/ACK顺序；即使这些设置开启，也没有持久SSD延迟或掉电耐久证据。本层不承诺产品SLO、Win11容量、真实ERP表现或全栈资源优势。

### 第二层：Linux + Windows Server PG18普通兼容与候选包

以PG18为主，在Linux和原生Windows Server上绑定精确被测提交、测试清单、checkout/tree及实际二进制。检查真实`core.sql`完成标记、JUnit无静默跳过、源码安装与候选归档重装、归档全部文件散列、普通升级/回滚与正常事务语义。PG18独立rhea互操作须绑定其版本、锁文件和实际TLS/settlement记录；共用Proton的客户端不能单独当跨引擎证明。

当前仓库记录七计划候选CI `36720731289`：head `450681d71c2fefef0a92e57098643701dabcf4f5`，实际checkout `191d9947d181aab14667562513eae54109a7ea54`，Linux/Windows Server2022 × PG18/17/16两轮共464项、12个core标记，PG18每轮44项、PG16/17每轮36项。当前PR2与该head的`src`、`include`、`sql`、`CMakeLists.txt`、`echoo_pgmq.control`、`tests`与`scripts/run_integration.py`无差异；这不是宣称当前文档head重新跑过CI，也不是本稿重新审计了远端归档。

普通兼容不等于性能通过；Windows Server不替代Win11。安全、parser、fuzz、新故障活动继续暂停，`blocked_security_review`保留；本稿不安排恢复这些测试，不把普通升级/回滚覆盖写成完整升级故障资格。候选仍不具备完整生产就绪结论。

### 第三层：后续真实Win11/SSD/ERP共同验收

在目标机器、真实持久SSD和同库部署条件下，使用共同确认的ERP事务结构、数据规模、并发、消息分布及实际门店到达模式，分别验证ERP独立运行和ERP+队列。原生AMQP路径与业务事务内SQL入队按实际占比分列，保留同事务容量锁等竞争成本。

只有真实峰值、代表性业务预算及以下待决参数冻结后，才能判定“2倍峰值无持续积压”和业务延迟达标。此层尚未完成；本稿是准备材料，不启动联调或任何暂停的资格活动。

## 3. 延迟：保留原评分，同时讨论绝对值与相对值组合

每个有效配对、每个事先约定窗口同时报告：基线p95 `B`、混跑p95 `Q`、绝对差 `Δ=Q−B`（ms）、相对差 `r_observed=Δ/B`，另列p50/p99/max、样本量、到达率和积压。基线为0、样本不足或环境门禁无效时不强算百分比。增加绝对差列是补充事实，**不改变通过条件**。

旧字段`provisional_db_p95_le_10_percent`继续按原规则输出true/false/null；历史未通过保持未通过。不要因“绝对只多一点”改写旧结果。

**待审阅候选，尚未批准：**在真实ERP联调中，对每类关键事务、每个验收窗口，考虑同时满足：

1. 混跑p95不超过该事务绝对预算 `L95`，必要时另设p99预算 `L99`；
2. 额外p95延迟 `Δ ≤ max(A95, r95 × B)`；
3. 实际业务到达/完成要求与积压规则同时达成。

其中`A95`是经业务认可的最小绝对容差，`r95`是相对容差。现有10%可作为`r95`讨论起点，但没有因此批准新公式；`A95/L95/L99`均未给定。此组合让很小的基线不会仅因分母小就失去业务解释，同时由绝对上限限制总响应时间。它可能放宽旧10%判定，因此必须明确审阅、版本化并仅用于获批后的指定场景；若未获批，仍只报告绝对差和旧10%评分。

消息侧分别约定“开始发送→生产者收到Accepted”及“开始发送→消费者收到消息”的绝对p95/p99预算，必要时单列“业务处理完成”。现有脚本E2E时间戳取在收到消息后、checksum验证和consumer ACK之前，不能标成“校验/ACK已提交”。任何新终点需单独记录和命名，不混算历史结果。

## 4. 待定参数与冻结办法

| 待定项 | 冻结所需输入与决定 |
|---|---|
| 门店峰值、2倍负载 | 代表性繁忙周期的到达记录；明确峰值窗口、持续时间、突发形状、消息大小分布、生产/消费数及ERP并发；先保留原始到达，不用已完成量倒推峰值 |
| 业务和消息延迟预算 | ERP关键事务负责人确认实际可接受响应时间与额外预算；确定服务时间/含排队响应时间、p95/p99、`A95/r95/L95/L99`及消息端点预算 |
| 窗口与重复 | 预设窗口长度、最小样本量、重复次数、基线稳定规则、需要各窗口满足还是允许何种例外；长尾不可被整场均值掩盖 |
| 资源余量 | 固定CPU型号/物理与逻辑核、OS/PG版本、SSD/文件系统/写缓存、ERP+PG配置；按目标机器为OS、ERP、队列及后台任务分配CPU/内存/磁盘预算 |
| 长稳与积压 | 约定业务周期覆盖、运行时长、checkpoint/autovacuum覆盖、表膨胀与资源趋势、可接受积压斜率/观察窗口、排空时限；24小时尚非已冻结要求 |

实际流程：先收集代表性工作负载和已有ERP预算 → 在目标机器做获授权的普通基线校准 → 形成一页版本化参数表及示例判定 → 用户/业务负责人明确确认 → 对冻结版本运行并评分。校准数据保留，不先看候选成绩再调线。每次改参数留下理由、生效场景和日期，不倒改旧分数；参数未定时结果标“未能验收”，继续报告可核验的机制与兼容进展。

## 5. 每轮必须留下的证据

- **负载口径：**同时记录计划到达、实际尝试、Accepted、有效唯一接收及业务完成；说明开放到达或闭环背压。单条等待Accepted会在变慢时自行少发，不能用低积压证明达到外部到达能力。未达到预定负载则不能判该负载通过。
- **窗口和对账：**预热、测量、排空边界分开；延迟以测量窗开始的cohort为准，跨窗完成保留，未完成不得丢弃；吞吐按固定窗口完成事件另算。逐窗从原始样本重算p50/p95/p99/max，不平均p95冒充总体p95。保留run ID、消息ID、attempt/delivery/settlement关联、正文校验结果和最终队列状态，分别核对丢失、合法重投、重复发布与多余ID。
- **资源和长稳：**CPU计量覆盖整个相关服务栈，同时列CPU秒、平均核数及每实际完成消息成本；短暂后台进程未覆盖时只能称已观测子集。客户端和采样器是否计入必须明示。内存说明cgroup/进程私有内存/共享页/文件缓存口径，不把RSS求和当唯一物理占用；记录峰值、趋势、采样间隔及遗漏。保留真实ready/unacked/retained与应用未接收积压区别，记录WAL、checkpoint、vacuum、磁盘增长和排空结果。
- **来源和终态：**保存精确提交、实际加载库/包散列、依赖/配置、原始逐条记录、资源样本、失败/无效/未运行清单及manifest；分列“机制可比”“普通兼容”“业务目标”“未验收资格”，不压成单个绿灯。
- **RabbitMQ如纳入后续比较：**相同主机、AMQP1.0、mTLS/证书校验、消息正文与元数据、持久队列/消息、远端Accepted、手动ACK、credit/inflight、实际工作量及暖机/窗口。echoo侧PG+worker与Rabbit侧PG+RabbitMQ/Erlang按同一整栈预算核算；注明单节点classic与复制/quorum差异。比较用于理解代价，不增设全面胜出要求。

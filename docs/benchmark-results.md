# 普通固定负载实测结果：2026-09-30

## 结论

这轮同总预算实验完成了全部 **27/27 单元**，每单元 **30秒预热 + 120秒测量**。正常流量的收集、校验和最终排空通过；这不代表候选性能目标通过。

- **1,077,932** 条消息的全部阶段尝试数、Accepted数和唯一接收数一致；观察到 **0 丢失、0 重复、0 校验/run-ID错误、0 发布失败**。echoo 共538,311条，RabbitMQ共539,621条
- **DB p95相对同轮基线增幅≤10%未通过**：echoo **12/12** 单元未达标，RabbitMQ **10/12** 未达标。两组共22/24未达标，阈值没有更改
- 两者的实际完成率均接近设定200/400条/秒，但不能写成所有单元精确达到目标。echoo最弱单元的发送到达率为目标的 **98.929%**，实际完成 **395.725条/秒**，目标为400
- 在本轮指定模式内，echoo的端到端p95/p99和服务端资源结果没有显示优势。不得据此推广为代理的一般优劣、最大容量、真实ERP影响或Win11性能结论

## 实际资源、版本与语义

27个单元的容器前后配置、cgroup与PG设置均核对；每单元拥有不同的新`/state` Docker数据卷。工作树干净，所有单元使用同一个不可变image ID：`sha256:c75bcf243e9d13b7ef3288e0d67d3408995d6a25984953b9c0f7d0601eec45a8`。

- **整个服务端栈共用2个逻辑CPU（0–1）、4GiB RAM、0 swap**，不是每个服务各得一份。`cpu.max=200000 100000`、`memory.max=4294967296`、`memory.swap.max=0`，PID上限512；echoo包含PG+worker，RabbitMQ包含PG+RabbitMQ/Erlang
- 客户端、合成DB客户端及采样进程使用另外两个CPU（2–3），在服务端预算外。runner可见4个逻辑CPU、约15.61GiB内存；这不是总机4GiB实验
- Ubuntu 24.04.5，Linux 6.17.0-1022-azure，Docker 28.0.4，runner image `20260920.314.1`；PostgreSQL **18.6**、RabbitMQ **4.0.5**、Proton C/Python **0.40.0**、Python **3.12.14**、psycopg **3.3.6**。完整依赖版本在原始`python-inputs.txt`和各`.stack/build-packages.txt`
- 标准`RelWithDebInfo`构建，`ECHOO_ENABLE_TEST_HOOKS=OFF`。本轮仅普通负载，没有恢复或运行暂停中的安全、fuzz、故障/崩溃资格验证
- 两侧PG读回均为`fsync=on`、`full_page_writes=on`、`synchronous_commit=on`、`wal_level=replica`、`autovacuum=on`；shared_buffers512MiB、max_connections40、max_wal_size1GiB、checkpoint_timeout300秒。echoo队列表为普通WAL表；RabbitMQ为单节点durable classic队列，非quorum/复制
- 两侧均为AMQP 1.0、mTLS+服务端名称校验、SASL EXTERNAL、1024字节正文、durable消息、发布者逐条等待远端Accepted、消费者手动Accepted、credit32。每发布连接最多1条未确认消息
- echoo轮询2ms、visibility60s、每link最多32 inflight；RabbitMQ Erlang scheduler配置为2、内存高水位512MiB，仍包含在同一个服务端4GiB总额内

每轮先测独立PG基线，代理/连接数/速率顺序按轮交替。每个客户端独立进程和连接。源方法与可复现命令见[性能方法](benchmark.md)。

## 对账、积压与失败保留

每个客户端的原始日志、`accounting.json`与摘要一致；所有消息单元最终真实队列深度为0，RabbitMQ同时核对ready/unacknowledged。没有发送/消费进程错误；普通服务器日志未发现ERROR/FATAL/PANIC记录，容器终态正常。

`backlog.json`是每秒按ID重建的应用层Accepted但尚未收到数量。该采样峰值echoo为3、RabbitMQ为1，有限观察窗口没有持续积压上升。echoo的`r1-echoo-1x1-400pps`和`r3-echoo-1x1-200pps`在测量窗口末各有1条尚未收到，最终都排空；其他单元窗口末为0。**这不是“所有时刻队列深度为0”，也不是代理内部ready/unacked连续时序。**

原始失败尝试、24个候选目标true/false值及所有慢单元都保留。工作流返回成功仅表示本轮正常流量/证据收集/对账完成，不替代性能资格。

## 下一步与结论边界

1. 优先解释和改善当前原生worker的消息尾延迟、DB p95增加和WAL/块I/O成本。轮询/调度、持久化事务与ACK路径是需要剖析的候选方向，尚未证明是根因；不应通过关闭fsync、降低持久化、改基线或改10%门槛获得“通过”
2. 任何代码/参数优化后，经授权在同样固定到达率、预算、确认语义下复测，保留全部重复轮次；另增加经授权的代表性业务到达结构与重复基线，以区分稳定差距和VM/相位噪声
3. 本轮每单元仅150秒活跃负载，短于300秒checkpoint_timeout；不覆盖长期checkpoint/vacuum周期、离线追赶、容量上限、24小时稳定、断电或复制语义。低平均CPU不能外推最大吞吐
4. 主验收仍需真实 **Win11 x64、4核/8GB/SSD、原生PostgreSQL18**。本轮是Linux云runner、容器约束的合成普通负载；没有实际ERP联调与门店硬件证据

本页只记录既有授权普通实验的结果与可验证限制，不触发新实验，也不恢复暂停的安全/故障资格流程。

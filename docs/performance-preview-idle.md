2026年9月30日完成的第二次诊断，使用固定 450681d 预览及 SQL 0.1.0。六阶段按预先声明顺序完成，含正常清理耗时 133.61 秒；前后基线门禁及漂移检查通过。0/1/4/8 个健康空闲消费者下，worker CPU 分别为单核的 0.138%/0.483%/0.966%/1.242%，worker PSS 为 5.49/10.11/10.68/11.43 MiB。内部四阶段均保持目标 200 TPS，各阶段前后快照均为空，未产生 MQ 消息。

8 连接阶段的合成 DB p95 为 0.698 ms，相对前/后基线分别低 3.69%/11.39%。同时，整体 PG CPU 比前/后基线高 1.248/1.402 个单核百分点，PSS 高 7.79/9.00 MiB，p99 高 0.222/0.057 ms。这些是短时顺序观察；暂定“真实 ERP/DB p95 相对劣化不超过 10%”标准尚未资格验收，不能据此宣称性能提升或达标。p99 是单独尾部观察，不是该 10% 标准。

本报告数值只来自成功的 attempt2。首次设施失败、根因探针和修复验证分别保留，未合并进第二次结果。产品二进制没有改动；修正的是测试控制器的正常关闭和证据落盘。

|---|---:|---:|---:|---:|---:|---:|
| PG-only 前 | 20 | 199.95 | 0.725 | 1.386 | 4.205 | 不适用 |
| 监听器 0 连接 | 15 | 200.00 | 0.752 | 1.351 | 4.552 | 0.138 |
| 1 空闲连接 | 15 | 200.00 | 0.635 | 1.158 | 4.414 | 0.483 |

本报告“全 PG”实际指采样到的服务进程及合成 DB 服务端 backend 集合。CPU 只对 PID 与创建时间匹配的稳定集合求差，不包括 Node、Python 客户端或采样器；可能遗漏两个采样点之间完全产生又退出的进程。PSS/USS/RSS 是每个样本先汇总该进程集合，再取样本中位数，单位 MiB；偶数样本取排序后的上中位值，与原计算一致。这些数值不是峰值，也不代表长期驻留内存。

| 阶段 | 全 PG PSS | 全 PG USS | 全 PG RSS 汇总 | worker PSS | worker USS |
|---|---:|---:|---:|---:|---:|

PSS 按共享者分摊共享页，可用于观察该进程组的驻留内存份额；USS 仅统计私有页，共享关系变化会让它跳变；RSS 对每个进程完整计入共享页，汇总会重复计数。这三者不是可互换的内存占用口径，也不能直接从 worker PSS 推导整体 PG 增量或内存泄漏。

## 门禁与计量方法

- 预声明顺序为 PG-only 前、监听器 0 连接、1/4/8 空闲连接、PG-only 后；观测共 130 秒，正常生命周期目标 180 秒。没有缩短阶段、修改阈值或自动重试。
- 前后 PG-only 各测 20 秒，整窗及两个 10 秒半窗的开始率、完成率均须至少 190 TPS，且无错误。前基线整窗 199.95 TPS，半窗 200.0/199.9；后基线整窗及半窗均 200.0。
- 前后完成率绝对相对漂移为 0.0250%，低于 5% 门禁；p99 绝对漂移为 0.164227 ms，低于预声明 `max(1ms, 前基线 p99 的 50%)`，本次界限为 1 ms。这是环境门禁，不是 p95 产品验收标准。
- 吞吐按固定窗口中的完成事件计数，延迟按窗口内开始的事务计入，包括迟到完成。原始暖机与测量行保留。事务固定为 1000 行合成库存上的单行 UPDATE 加 100 行范围 SUM，目标 200 TPS，不追赶积压突发。每阶段前在测量外恢复 quantity 并 VACUUM ANALYZE。
- CPU 计数分辨率为 10 ms（100 Hz）。worker 的 0/1/4/8 连接阶段 CPU 增量仅 0.02/0.07/0.14/0.18 秒，因此小百分比是粗粒度观察。按实际约 14.5 秒 CPU 采样跨度，单个 tick 约相当于 0.069 个单核百分点。
- CPU 每 0.5 秒采样，末点位于名义测量结束前 0.5 秒，避免 DB backend 已退出造成整段 CPU 丢失；按实际约 19.5 秒或 14.5 秒跨度归一化，并重算该跨度中的 DB 完成数。只比较相同 PID 与创建时间的 CPU 差。所有记录样本的进程集合均稳定；两次采样之间完全出现又退出的进程仍可能未被观察。
- 8 个队列及消费 ACL 均在全部观测前创建；每个消费者有独立空队列、32 credit、双向 TLS 及服务器名校验，使用 SASL EXTERNAL。测量前后核对实际健康连接数、socket 数及空消息表，没有 MQ 消息生产。
- 已独立复算成功尝试的 60 个原始结果文件，验证内容哈希、六阶段数值及同一 executor 内的正常清理。所有 PG/Node/DB 进程退出，PID 文件消失。

## 失败尝试和设施修复

首次 attempt1 在 1 连接阶段正常 AMQP 关闭后，控制器只等进程 1 秒便报错。其 PG-only 前和 0 连接阶段完成；1 连接的 DB 原始行与健康/空队列快照保留，但内存中的资源样本未落盘；4/8 连接和后基线未执行。原 executor 内 Node 的最终退出码未获确认，这个不确定性原样保留。首次数据未与第二次合并。

独立 close-probe 在 7.43 秒内查明：AMQP 确认后 0.862 ms 就出现正常 TLS socket close，随后 6.5 秒无 TCP socket 但 Node 仍活着；父进程关闭 stdin 控制管道送出 EOF 后约 4.875 ms，观察到真实 exit code 0。原因是测试控制管道未关闭，未要求修改产品/TLS。

attempt2 控制器只修正一次性 EOF、幂等关闭/回收、分别记录握手/socket/进程里程碑、覆盖既有 5 秒宽限的等待，以及先落盘观测再关闭客户端。单连接 close-fixture 用完全相同的方法验证通过，耗时 0.912 秒；Node 网络客户端、产品、130 秒计划及全部门禁保持不变。

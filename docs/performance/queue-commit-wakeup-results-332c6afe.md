# Queue-directed post-commit wake: candidate rejected pending revision

Candidate: `332c6afee1dab46132eabf77eacd42cd82305ec3`
Baseline: `115dcfe67c1dc2ebd2bfc004ed9ce0700947ce40`
Draft PR: https://github.com/MixGeeker/echoo_pgmq/pull/12

The isolated wake candidate improves Windows sparse-delivery tails, but causes a
large repeatable Linux sparse-burst regression. Do not merge this candidate.
An unchanged C candidate should not be selected based only on Windows results.

full_page_writes and synchronous_commit on. These are shared CI runners, not
Windows11 or representative store capacity. One connection carries a publisher
and receiver. Three fresh-cluster pairs per platform alternate AB/BA/AB.

completions. Each expected send has Accepted, receive and remote-settled

## CPU and instrumentation limits

CPU is the worker's user+system seconds over the whole client cell, including
TLS/link lifecycle; percent is one-core normalized, not whole-machine percent.
Windows sparseW32 median CPU seconds0.2031→0.2812; equal-message paired cost
rises27.3–38.5%. Linux sparseW32 median0.24→0.30, paired+16.7–30.4%.
Its CPU% falls9.95→4.52 only because the same work now spends much longer
waiting; that is not an efficiency gain.

Five-second credited-idle median one-core CPU is Windows0.303→0.303%,
Linux0.785→0.785%. Windows resolution is15.625ms; one candidate idle arm
doubles from one tick to two. Short low-signal CPU readings do not establish
zero overhead. No idle power claim is supported.

Boundary lock-wait counts are zero but cannot exclude transient locks.
pg_stat_wal snapshots lag worker reporting: many active backlog deltas are0,
and bootstrap stats arrive during the first idle cell. They cannot measure
per-cell WAL cost or attribute this regression. Do not use them as proof of
storage equivalence. A future run should use synchronous WAL-LSN boundaries
for generated bytes and suitable worker-phase or syscall evidence for waits.

## Diagnosis and next step

On Linux the candidate first delivers quickly, then repeatedly develops about
40–42ms gaps shared by receive, publisher Accepted and receiver settlement.
For example candidateW32's first cohort receives messages at4.1,5.4,7.1,8.1,
49.0,50.3,91.0,92.5,134.1,135.5,176.9,178.2ms after the first send.
All32 sends were queued quickly; this is not the150ms inter-batch pacing.

The server's accepted sockets do not set TCP_NODELAY. rhea's receiver creation
sets it client-side by default. This timing is consistent with an interaction
between smaller interleaved writes and Nagle/delayed ACK, but no packet trace
or TCP/syscall evidence was captured, so this is a hypothesis.

Recommended next isolated comparison: baseline, TCP_NODELAY alone, and
queue-wake+TCP_NODELAY, retaining this wake-only result as a failed arm. Verify
socket-option success/failure behavior and ordinary semantics first; preserve
poll50ms, durable commits, traffic, pairing and default system timer settings.
Do not add early flushing or nearest-deadline changes simultaneously. No new
experiment has been started from this report.
